# WB CLI - Claude Code Instructions

## How to Resume Implementation

1. Read `docs/PROGRESS.md` — current version, phase status, and what comes next.
2. Read `docs/DESIGN.md` — architecture decisions and command taxonomy.
3. Say **NEXT** to implement the next pending phase.

Each phase follows this pattern:
- Implement in `src/wb/` following the file layout in `docs/DESIGN.md`
- Write tests in `tests/unit/`
- Run `pytest tests/unit/ -v` — all must pass
- Run the `phase-complete` skill to finalize (version bump, CHANGELOG, commit)

```bash
# Activate env (Windows)
source .venv/Scripts/activate
```

## Coding Rules

- Single quotes for all strings
- Python 3.11+ syntax: `X | None`, `list[str]`, `match/case`
- No `typing.Optional`, `typing.Union`, `typing.List`, etc.
- `snake_case` for functions/variables, `PascalCase` for classes, `UPPER_SNAKE_CASE` for constants
- Google-style docstrings on all public API
- Functions ≤ 30 lines, max 3 nesting levels
- No hardcoded URLs, paths, magic numbers — use `constants.py`
- Never log secrets; mask tokens as `key[:4]...key[-4:]`

## Exit Codes

| Code | Error code | Meaning |
|------|------------|---------|
| 0 | — | success |
| 2 | `VALIDATION_ERROR` | input validation failure |
| 3 | `AUTH_FAILURE` | authentication failed (bad/expired token) |
| 4 | `AUTH_MISSING_SCOPE` | token lacks required scope |
| 5 | `RATE_LIMITED` | 429 after retries exhausted |
| 6 | `API_ERROR` / `UPSTREAM_ERROR` | WB API error — `UPSTREAM_ERROR` is raised specifically after 5xx (500/502/503/504) retries exhaust, so agents can distinguish WB infra stress from a true rate-limit event |
| 7 | `CONFIG_ERROR` | config/profile error |

5xx retries use a longer backoff schedule (5 s → 15 s → 45 s + jitter) than 429 retries, because WB gateway failures rarely clear in a couple of seconds and aggressive retry just amplifies the storm.

## Response Cache

Idempotent past-day responses from `stats product-spend`, `stats daily-report`, and `analytics sales-funnel products/history/grouped` are cached on disk at `~/.wb-cli/response_cache.db` (SQLite WAL). Same-day or future-dated queries bypass the cache entirely — so live data is never served stale.

- Cache is keyed by endpoint + token fingerprint + params (tokens themselves are never stored, only a SHA-256 prefix).
- Cross-process safe: a second `wb` invocation running the same past-day query gets a hit without touching WB.
- Retention: 90 days; old rows are pruned on access.

## Authentication

### Credential Resolution Priority (post A-2)

Runtime commands resolve credentials in this chain (highest to lowest):

```
--profile <name> flag  >  active profile  >  ConfigError (exit 7)
```

Environment variables and `.env` files are **bootstrap-only material for `wb auth login` / `wb auth login-portal`** — they are no longer consulted by runtime code. The fix closes the F-19/F-20 fingerprint-drift trap by construction: a stale `.env` next to a healthy profile can never silently override it again. Run `wb auth whoami` to confirm which credentials runtime code will use.

To check which credential is in flight:

```
$ wb auth whoami
Profile     : 668554_base
Source      : active-profile        # or 'profile-flag' when --profile <name> was passed
Seller ID   : 668554
Token type  : base
Token (promotion): a1b2c3d4e5f60718
Portal      : not configured
```

### Auth Methods — official vs unofficial

The CLI supports two completely different authentication paths. They are **not interchangeable** — pick the one that matches the endpoint you need to call.

1. **`wb auth login` — OFFICIAL WB API token (JWT)**

   The documented authentication path. The JWT is generated by the seller via the WB seller portal UI under "API tokens" and sent in the `Authorization` header (raw JWT, no `Bearer` prefix).

   Used for every documented endpoint surface — promotion (`/api/advert/...`), analytics (`/api/v2/...`), statistics (`/api/v1/...`), content, marketplace, finance, prices, supplies, feedbacks, buyers-returns, documents (11 token categories total).

   - `wb auth login --token <JWT> --category promotion`
   - `wb auth login --token <JWT> --category all` — saves under all 11 categories at once
   - `wb auth categories` — list valid `--category` values (table or `--json`)

2. **`wb auth login-portal` — UNOFFICIAL seller-portal session**

   Logs into the WB seller portal (`https://seller.wildberries.ru`) the same way the manager's browser does — by replaying `authorizev3` + `cookie` headers copied from a logged-in browser session. **There is no public documentation for these endpoints**; they may change without notice.

   Used only to reach data the official API does not expose. Today that means:
   - `wb portal products` — richer per-product cards via the portal `tableListv6` endpoint (vendor codes, stocks, ratings, feedback counts).
   - `wb portal bids` — CPC/CPM bid recommendations with per-tier reach forecasts via `cmp.wildberries.ru/api/v1/advert/bids[-cpc]`. The only bid-recommendation surface for CPC campaigns (official `/api/advert/v0/bids/recommendations` is CPM-only). Empiric reference: [docs/portal/](docs/portal/).
   - `wb auth generate-token` — render-token generation via the portal JRPC endpoint.

   Both `--authorizev3` and `--cookie` are required (the `wb-seller-lk` session token is NOT needed).

**Rule for agents:** if a documented endpoint can answer your question, use `wb auth login` and the official command tree (`campaign`, `bid`, `budget`, `stats`, `analytics`, …). Only fall back to `wb auth login-portal` + `wb portal …` for fields the official API genuinely does not expose.

Both methods can coexist on the same profile — the active profile carries an `Authorization` JWT *and* a portal session in parallel.

### Environment Variables

Post A-2, all `WB_*` credential env vars are **bootstrap-only**: they are read once by `wb auth login` / `wb auth login-portal` to materialize a profile and then ignored by every other command. Runtime always reads from `~/.wb-cli/profiles.json` (or the `--profile <name>` flag override).

| Variable | Purpose |
|----------|---------|
| `WB_API_TOKEN` | Bootstrap JWT for `wb auth login` (no `--token`). Defaults `--category` to `all` in bootstrap mode |
| `WB_ANALYTICS_TOKEN` | Bootstrap JWT for `wb auth login --category analytics` (preferred over `WB_API_TOKEN` when category is analytics) |
| `WB_AUTHORIZEV3` | Bootstrap portal authorizev3 for `wb auth login-portal` (no `--authorizev3`) |
| `WB_PORTAL_COOKIE` | Bootstrap portal cookie for `wb auth login-portal` (no `--cookie`) |
| `WB_RATE_LIMITER` | Set to `memory` to force the in-process limiter and skip the shared SQLite coordinator (diagnostic only) |

> **First-time setup with `.env`:** drop a `.env` containing `WB_API_TOKEN=<jwt>` next to your project, then run `wb auth login` once — the CLI bootstraps a profile under all 11 categories and you never need to touch the env var at runtime again. Use `wb auth whoami` to confirm which credential is in flight.

## Rate Limits

- **Authoritative reference**: `RATE_LIMITS.md` — maps every CLI command → endpoint → limit → source
- **Machine-enforced**: `src/wb/core/rate_limits.py` — endpoint→(calls, period) map consumed by `_factory.py`
- **Implementation**: `src/wb/core/rate_limiter.py` — `SharedRateLimiter` (SQLite WAL at `~/.wb-cli/rate_limits.db`) by default, `RateLimiter` (in-process) as the fallback. The shared limiter serialises parallel `wb` processes so WB sees a combined call rate that respects the per-token budget. Set `WB_RATE_LIMITER=memory` to force the in-process limiter.
- The CLI throttles **preemptively** — agents do not need to add sleeps between calls
- Most critical: `EP_CAMPAIGN_FULLSTATS` → 1 call/20 s (burst=1), analytics funnel/history → 3 calls/min

### Known WB API Quirks

| API | Field/Behavior | Wrong assumption | Correct behavior |
|-----|----------------|-----------------|-----------------|
| Analytics v3 `sales-funnel/*` | `selectedPeriod` start key | `begin` | `start` |
| Analytics v3 `sales-funnel/products/history` | Date range limit | Any 30-day window | Max ~7-day lookback; farther dates → 400 |
| Analytics v3 `sales-funnel/products/history` | Rate limit | Same as other endpoints | 3/min, 20s interval — CLI enforces preemptively |
| Analytics v3 `sales-funnel/products/history` | Unknown NM IDs | Returns empty list | Returns 400 — only use real seller NM IDs |
| Promotion `/adv/v3/fullstats` | Campaigns with no data | Returns empty list | Returns HTTP 400 — don't call for never-started campaigns |
| Promotion `/adv/v3/fullstats` | Rate limit | Relaxed | 3/min, burst=1 → CLI enforces 1 call/20 s |
| Normquery `/adv/v0/normquery/list` | `items` field | Always a list | Can be `null` — use `(raw.get('items') or [])` |
| Analytics v3 `sales-funnel/products/history` | `dt` date field | `dt` key | Returns date in `date` key — `FunnelHistoryDay.from_api` reads `date` with `dt` fallback (F-18) |
| Promotion `/api/advert/v0/bids/recommendations` | Query params + scope | Single `id`, returns a list, any payment type | Requires **both** `nmId` AND `advertId`; returns one object per call (per item). CPM campaigns only — non-CPM yields HTTP 400. CLI loops per NM (F-19) |
| Promotion `/api/advert/v1/bids/min` | Method/shape | GET like recommendations | **POST** with JSON body `{advert_id, nm_ids[≤100], payment_type, placement_types}`; returns `{bids[].{nm_id, bids[].{type,value}}}` (F-19) |
| Promotion `/api/advert/v2/adverts` | Per-item current bids | Need separate bid endpoint | Live per-NM bids already in `adverts[].nm_settings[].bids_kopecks.{search,recommendations}` — `wb bid get-items` reads these directly with zero extra API calls (F-19) |
| Analytics `search-report` | Any API token | Works with standard token | Requires `Analytics/Advanced` scope — returns HTTP 403 |
| Promotion `/adv/v1/budget/deposit` | `sum` field unit | Kopecks | Rubles — minimum 1000, must be multiple of 50 |
| Portal `cmp.wildberries.ru/api/v1/advert/bids[-cpc]` (UNOFFICIAL) | Response shape | One stable shape per endpoint | Top-level keys are driven by `bid_type`: `1` (manual) → `{combined: [...]}`; `2` (unified) → `{search: [...], recommendations: [...]}`. CPC and CPM endpoints share these rules. `wb portal bids` parser surfaces whatever placement keys WB returns (F-21). |
| Finance `/sales-reports/*` + `/acquiring/*` | Report lifecycle | Async generate-then-fetch | **Pre-generated by WB on a fixed schedule** (weekly default, daily if seller opted in). No "create report" step — these endpoints are pure read-only views over files WB already published (I-22). |
| Finance `*/detailed*` `rrdId` cursor | Pagination semantics | Reset to 0 per page or use offset | Pass last response row's `rrdId` as the next request's `rrdId`. 204 = end of stream. Each page is one API call subject to the 1/min throttle — exhausting a 1 M-row seller via `wb finance … detailed --all` takes 10+ minutes (I-22). |
| Finance `/{list,detailed}` date filter | Date-range semantics | Filters on `createDate` (when WB generated the report) | Filters on the **reporting period** (`dateFrom`/`dateTo`). A report covering 2026-05-01…2026-05-07 with `createDate=2026-05-15` appears when you query `to=2026-05-07`, not `to=2026-05-15` (I-22). |
| Finance `reportId` field | Numeric type | Standard 32-bit int | **int64** — Python handles natively, `json.dumps` preserves precision. The swagger flags daily reports specifically as needing big-int handling — no special CLI code is needed because Python `int` is unbounded (I-22). |
| Portal `seller-weekly-report.../{type}/xlsx/{id}` (UNOFFICIAL) | Download payload | Raw xlsx bytes (like Jam returns a zip) | **JSON envelope** `{"data": "<base64 xlsx>", "error": false, "errorText": "…"}` — must check `error` first, then base64-decode `data`. Pending state = `error: true` OR empty `data`. The list endpoint has no status field, so a successful download IS the readiness signal (I-25). |
| Finance `/sales-reports/detailed` rows | Net payout | `forPay` is the final net per row; subtract it from revenue for WB cost | **Wrong** — `forPay` is gross payout present **only on sale rows**; logistics/storage/deduction/penalty/acceptance sit on **separate `forPay=0` rows** and are subtracted from it. Settlement identity (live-verified to the kopeck): `bank_payment = Σ forPay − Σ logistics − Σ storage − Σ deduction − Σ penalty − Σ acceptance`. `revenue − Σ forPay` yields negative costs / >100% margins. Storage & deductions carry **no `nmId`** (period-level); only commission/acquiring/logistics attribute per SKU. `commission` (`ppvzSalesCommission`) and `acquiring` are already netted inside `forPay`, not additive (I-26). |
| Portal `seller-weekly-report.../{type}/order` (UNOFFICIAL) | Idempotency | Re-POSTing returns the same id | **Not idempotent** — every POST mints a new id with a fresh trailing nonce (`supplier-goods-{seller}-{from}-{to}-{nonce}`). Poll by attempting the download, not by re-POSTing (I-25). |
| Portal `seller-weekly-report.../{type}/order` (UNOFFICIAL) | Date format in query | ISO `YYYY-MM-DD` | **`DD.MM.YY`** (day-first, two-digit year) in the URL query string. CLI formats via `format_query_date` and guards `year < 2000` to avoid wraparound (I-25). |

## CLI Output Rendering Pattern

`OutputRenderer.display()` is **JSON-only**. For table mode it passes `data` straight to
`render_table()` which calls `table.add_row(*row)` — this only works when `data` is a
**list of lists** (strings). Passing a list of dicts produces the dict *keys* as cell values.

**Rule:** Every command must branch on `renderer.is_json`:

```python
if renderer.is_json:
    typer.echo(json.dumps([asdict(s) for s in results], indent=2, ensure_ascii=False))
    return

from wb.core.output import render_table
rows = [[str(s.field_a), str(s.field_b), ...] for s in results]
render_table(['Col A', 'Col B', ...], rows, title='My Table')
```

The `--fields` filtering from `renderer.display()` only works in JSON mode.

## Null-Safety Pattern for WB API Responses

```python
# Wrong — crashes on null
for item in raw.get('items', []):

# Correct — handles null and missing key
for item in (raw.get('items') or []):
```

## Key Design Decisions

- Promotion = execution core; Analytics = discovery extension (separate tokens)
- All mutations support `--dry-run`; never auto-apply without explicit confirmation
- `--json` flag on every command for agent/script compatibility
- Multi-profile from day one — no single-account shortcuts
- Optimizer is recommendation-first; mutations only with `--apply`

## Financial Data Surface

Several distinct "money" surfaces — pick the right one:

| Command | API | What it shows |
|---------|-----|---------------|
| `wb budget balance` | `/adv/v1/balance` (promotion) | Ad-deposit balance — money pre-funded for ad campaigns |
| `wb report sales` / `orders` | `/api/v1/supplier/{sales,orders}` (statistics) | Per-sale/order transaction log (saleID, finishedPrice, warehouseName) |
| `wb finance sales-reports …` | `/api/finance/v1/sales-reports/*` (finance) | **Settlement statements** — what WB owes the seller after logistics/storage/acquiring fees |
| `wb finance acquiring …` | `/api/finance/v1/acquiring/*` (finance) | Acquiring (card-processing) fee breakdown |
| `wb portal campaign finance` | `cmp.wildberries.ru/api/v6/upd` (UNOFFICIAL portal) | Per-deduction ad-spend ledger ("История затрат") — campaign × charge-date × payment-source rows. Paginated JSON; `--page N` for a slice, default auto-fetches the full date range. |
| `wb portal campaign finance-xlsx` | `cmp.wildberries.ru/api/v5/updxlsx` (UNOFFICIAL portal) | Same ledger as a downloadable xlsx workbook (full range in one call). |
| `wb portal sales-report supplier-goods` | `seller-weekly-report.wildberries.ru/.../supplier-goods/{order,orders,xlsx}` (UNOFFICIAL portal) | Per-SKU per-day orders/sales xlsx workbook ("Отчёт по товарам"). Async 3-step (generate → poll → download) hidden behind a single command. Daily/weekly/monthly = different `(--from, --to)` shapes. |
| `wb economics product` | warehouse-remains (analytics) + `/api/finance/v1/sales-reports/detailed` (finance) | **Derived per-product unit economics** — joins current stock with settlement costs into per-SKU margin. Exact mode (default) shows only nmId-attributable costs (commission/acquiring/logistics); `--apportion` folds period storage+deductions pro-rata by revenue. Always emits a period reconciliation. Requires both analytics + finance tokens. |

Settlement reports are pre-generated by WB on a weekly schedule (daily if the seller opts in). The CLI has no "create report" step — `list` discovers existing reports; `detailed` returns line items. Date filters apply to the **reporting period** (`dateFrom`/`dateTo`), not the report creation date.

The two `wb portal campaign` commands hit the seller-portal expense ledger that the documented analytics API does not expose. They require `wb auth login-portal` (cookie + authorizev3) — same surface as the rest of `wb portal`. Dates are sent as start-of-day MSK (`YYYY-MM-DDT00:00:00+03:00`); WB treats `to` as inclusive end-of-day.
