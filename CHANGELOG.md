## v0.45.0 (2026-05-31)
- I-24: `wb portal campaign finance{,-xlsx}` — two synchronous portal commands surfacing the `cmp.wildberries.ru/campaigns/finances` expense ledger ("История затрат") that the documented analytics API does not expose. `wb portal campaign finance --from YYYY-MM-DD [--to YYYY-MM-DD] [--page N] [--page-size N]` wraps `GET /api/v6/upd` (paginated JSON; default auto-paginates the full date range, `--page N` returns just that slice); renders a rich table by default with a `Total: X ₽ across Y rows` summary header, or JSON via `--json`. `wb portal campaign finance-xlsx --from YYYY-MM-DD [--to YYYY-MM-DD] [-o PATH]` wraps `GET /api/v5/updxlsx` (one-shot binary download, returns the whole ledger in one request) and writes a kebab-case `campaign-finance_<from>[_<to>].xlsx` file; `--json` swaps row output for `{saved_path, byte_size, from, to}` metadata. New `CampaignFinanceEntry` + `CampaignFinancePage` dataclasses (`from_api()` parsers tolerate missing/null fields), `PortalCampaignFinanceService` orchestrator with `list_page` / `list_all` (loops until short page or `total_count` reached) / `download_xlsx`, and a `format_msk_datetime` helper that formats start-of-day MSK timestamps (`YYYY-MM-DDT00:00:00+03:00`) the way both endpoints expect. **`PortalClient._get_bytes()` was refactored** to accept query params, an `include_auth: bool = True` flag, and overridable `origin`/`referer` headers — `cmp.wildberries.ru` accepts (and requires) `authorizev3`, the jam downloads CDN rejects it, so the same helper now serves both with an explicit per-caller choice. `download_jam_file` was updated to pass `include_auth=False` to preserve the prior CDN behavior; a regression test pins this. Also extends `_get()` with `origin`/`referer` overrides so the new finance list call can advertise the cmp host as its origin per the captured browser trace. New `campaign_app` Typer group registered under `portal_app` with name `'campaign'` as the extension point for future cmp.wildberries.ru commands; existing `_resolve_jam_output` was renamed to `_resolve_download_output` to reflect its new dual purpose. `CAMPAIGN_FINANCE_DEFAULT_PAGE_SIZE=100` and `MSK_TZ_OFFSET='+03:00'` join the constants module; `EP_PORTAL_UPD_LIST` and `EP_PORTAL_UPD_XLSX` register the endpoint paths. Live against `25169_personal` for 2026-05-11: paged JSON (`--page 1 --page-size 5`) returned 5 rows + the `Total: 193,925 ₽ across 159 rows` summary; **auto-paginate** (no `--page` flag) walked 2 API calls at the default `page_size=100` (100 + 59) and returned all 159 entries, the per-row `upd_sum` total matching `upd_total_amount` (193,925 ₽) exactly across both payment sources ("Баланс" + "Промо бонусы") and both bid types; xlsx download wrote a 13,375-byte workbook whose 160 rows (1 header + 159 data) match the JSON `total_count`. Confirmed empirically that the `bid_type` enum in `/api/v6/upd` is **opposite** to F-21's `_BID_TYPE_INT` (xlsx column "Раздел" shows `bid_type=1` → "Единая Ставка" / Unified, `bid_type=2` → "Ручная Ставка" / Manual) — the new `CampaignFinanceEntry` stores the raw int so callers can map without baking either convention into the dataclass. 32 new unit tests across 11 classes (dataclass parsing, MSK formatter, default filename, client headers/params/4xx-5xx, service auto-paginate, CLI table/JSON/xlsx/validation, plus the jam-CDN regression test); 1590/1591 total passing (same pre-existing `test_auth_list_empty` env-leak as I-23). CLAUDE.md "Financial Data Surface" table extended with two new rows for the unofficial portal commands so agents can pick the right "money" surface.

## v0.44.0 (2026-05-30)
- I-23: `wb portal jam` — new sub-command group that downloads WB Джем (Jam) seller-analytics reports via the undocumented async file-manager workflow (generate → poll until SUCCESS → download). First wired-up report type is `SEARCH_QUERIES_REPORT` ("Поисковые запросы — ваши товары") exposed as `wb portal jam search-queries --from YYYY-MM-DD [--to YYYY-MM-DD] [-o PATH]`; sibling `wb portal jam list` reads the portal's downloads index for already-generated reports. `JamReport` dataclass + new `PortalJamService` encapsulate the 3-step pipeline (client-generated UUID, payload-window math including the `previousStartDate`/`previousEndDate` same-length lookback, polling that matches on our own UUID). **Key reverse-engineering result**: the downloads CDN (`downloads-content-analytics.wildberries.ru`) requires an `x-download-token` header — cookie alone returns HTTP 403. The token is minted via the same `tokensjrpc` endpoint that already powers `wb auth generate-token`, but with `params={'team': 'content-analytics'}` instead of `'render'`; `PortalClient.generate_download_token()` wraps this and `download_jam_file()` mints just-in-time (TTL ≈ 5 min). `PortalClient.generate_token()` grew a `team` parameter (default `'render'`, backwards-compatible). The new `_get_bytes()` helper mirrors `_get()` but returns `response.content` and intentionally omits `authorizev3` for the CDN host (which rejects it). Live against `25169_personal`: `wb portal jam search-queries --from 2026-05-11` generated report `650ef595-…`, polled to `SUCCESS`, and wrote a 575 KB `.zip` containing a 660 KB `.xlsx` named "29-5-2026 Поисковые запросы — ваши товары с 11-05-2026 по 11-05-2026.xlsx". 38 new unit tests; 1558/1559 passing (same pre-existing `test_auth_list_empty` env-leak as recent releases).

## v0.43.0 (2026-05-27)
- I-22: `wb finance` — new command group exposing six WB Finance API endpoints (`finance-api.wildberries.ru`) so agents can finally see the settlement layer (what WB owes the seller after logistics/storage/acquiring fees). Distinct from `wb budget balance` (ad deposit) and `wb report sales` (per-sale transaction log). Two nested groups: `sales-reports list|get|detailed` and `acquiring list|get|detailed`. List endpoints return typed `SalesReportSummary` / `AcquiringReportSummary` dataclasses; detailed endpoints pass raw row dicts through losslessly (matches the I-21 pattern — protects against silent field drift when WB adds new fields). `--all` is opt-in for `detailed*` and `get <reportId>` and exhausts the `rrdId` cursor with help-text warning about the 1 req/min throttle (~1 min per 100 000-row page). Period-based endpoints rate-limited preemptively at (1, 60.0) Personal / (1, 3600.0) Base; the two `/detailed/{reportId}` template paths deliberately have no static prior because the URL embeds the report ID — `EndpointBudget` self-corrects from response headers if WB throttles. Cache policy: the four non-templated endpoints get 60 s TTL (Personal) / 1 h (Base) — once a report is published it never changes, so back-to-back agent calls share the response. CLAUDE.md gets four new Known-Quirks rows (pre-generated lifecycle, `rrdId` cursor semantics, date filter applies to reporting period not `createDate`, int64 `reportId` preserved natively by Python `json.dumps`) plus a new "Financial Data Surface" section disambiguating the three money-related command trees. Live against `25169_personal`: sales-reports list returned 17+ weekly statements for Apr–May 2026 with multi-million-RUB sums; acquiring list returned three monthly statements (Jan/Feb/Mar 2026). 49 new unit tests across three files; 1520/1522 passing (same pre-existing `test_auth_list_empty` env-leak as recent releases plus a timing-sensitive `test_acquire_after_window_clears_no_sleep` flake that passes in isolation).

The `StatisticsClient` factory now wires `with_rate_limits=True` + token-type — both endpoints (and the pre-existing internal `get_sales` used by `stock-runway`) now share the `EndpointBudget` 1/min throttle that swagger 12 documents, and both are cacheable at 60 s TTL (matches the rate-limit interval, so same-minute re-runs return cached).
